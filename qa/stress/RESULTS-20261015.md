# VM 壓力測試結果（2026-10-15）

測試對象：正式目前部署的程式（ri-backend:local／ri-frontend:local，commit 68abd2b），在獨立壓測環境執行，
設定與正式相同（gunicorn 2 個 worker、MySQL 預設參數 innodb_buffer_pool_size=128MB、nginx 60 秒轉發逾時、Audit 暫停）。
機器：4 核心、8 GB 記憶體（與正式同一台，正式系統當時閒置，沒有被動到）。

## 資料集
- 10,000 件案件：已確認 5,400（含 400 件批單）、已公布 1,500、草稿 3,100；每件 payload 平均約 11 KB（資料表 180 MB）
- SoA 交易列 18,000（`transactionRows`）；Accounting 的付款排程列 14,869；收款批次 1,981 筆（約 1/3 的已確認案件有收款，一半已人工確認）
- 7 位使用者：Reinsurance Staff×3、General Manager×1、Finance Staff×2、Finance Manager×1

## 回應時間（從送出請求到收完回應；不含瀏覽器解析與畫面繪製）
| 動作 | 1 個人 | 7 人同一秒同時 | 7 人平常使用 8 分鐘（中位／P90／最慢） |
|---|---|---|---|
| Accounting 頁（47 MB） | 23 秒 | 24–60 秒，**7 人中 3 人逾時 504** | 33 ／ 40 ／ 52 秒 |
| Dashboard | 8 秒 | 8–31 秒 | 13 ／ 26 ／ 31 秒 |
| Production Report | 8.5 秒 | 8–35 秒 | 15 ／ 28 ／ 32 秒 |
| 案件列表 | 2.4 秒 | 2.3–10.6 秒 | 5 ／ 17 ／ 29 秒 |
| 開啟一件案件 | 0.04 秒 | — | 中位 5.9 ／ P90 29 ／ 最慢 35 秒 |
| 存檔草稿 | 0.05 秒 | — | 8 ／ 16 ／ 19 秒（含載入） |
| 記一筆收款 | 0.13 秒 | — | 0.26 ／ 0.35 ／ 0.38 秒（POST 本身） |

## 為什麼
- 只有 2 個 worker，一次只能同時處理 2 個請求；Accounting 一次獨佔一個 worker 23 秒，後面的請求（包含只要 0.04 秒的）全部排隊。
- Accounting：每件案件重算交易明細（`transaction_details` 被呼叫 8,684 次，佔約 23 秒）、再整份 deepcopy／json_roundtrip（約 6 秒）；MySQL 讀取約 4 秒。
- Dashboard、Production Report：每次都把全部 1 萬件案件的 payload 讀出來重算（MySQL 讀取 5–7 秒）。
- 案件列表：單一 SELECT 1.9 秒（依 updated_at 排序時要連同 JSON payload 一起排序）。
- MySQL 緩衝區 128 MB 小於資料表 180 MB：一次 Accounting 有約 23% 的頁面要從磁碟讀（4,973 次實體讀取）。

## 重跑
```
qa/stress/up.sh                      # 以目前部署的映像建立獨立環境（約 30 秒）
docker exec -i ri-stress-backend python manage.py shell < qa/stress/seed.py     # 造 1 萬件資料（約 2.5 分鐘）
qa/stress/load.sh baseline --reps 3
qa/stress/load.sh burst /api/accounting --rounds 2
qa/stress/load.sh mixed --minutes 8 --think 5,20
qa/stress/monitor.sh start FILE / stop FILE / summary FILE     # 取樣 CPU／記憶體
docker exec -i ri-stress-backend python manage.py shell < qa/stress/profile.py   # 時間花在哪
qa/stress/down.sh                    # 全部刪掉
```

## 設定比較（同一份資料；MySQL 緩衝區 128→512 MB 另外標示）
| 設定 | 單人 Accounting | 7 人同一秒開 Accounting | 7 人平常使用 6 分鐘：Accounting 中位／最慢 | 開案件 中位／P90 | 錯誤 | 後端記憶體尖峰 |
|---|---|---|---|---|---|---|
| **現行**：2 worker、緩衝區 128MB（8 分鐘） | 23 秒 | 每輪 3/7 逾時 | 33 ／ 52 秒 | 5.9 ／ 29 秒 | 0 | 1.2 GB |
| 2 worker、緩衝區 512MB | 22 秒（Dashboard 6.7、Production 6.8、列表 1.6） | 每輪 3/7 逾時 | — | — | — | 1.2 GB |
| 3 worker、緩衝區 512MB | 22.5 秒 | 每輪 1/7 逾時（24–60 秒） | 24 ／ 36 秒 | 0.05 ／ 3.8 秒 | 0 | 1.8 GB |
| **4 worker**、緩衝區 512MB | 24 秒 | 每輪 1/7 逾時（29–60 秒） | 24 ／ 27 秒 | 0.04 ／ 0.09 秒（偶爾一次 18 秒） | 0 | 2.4 GB |
| 2 worker × 4 thread、緩衝區 512MB | 22 秒 | 14 個請求全部失敗（502／504） | 14/20 失敗 | — | 大量 | 超過 2.6GB 上限被 OOM 終止 |

結論：增加 worker 解決「排隊」（別人開 Accounting 時其他人不再被卡住），但不會讓單次 Accounting 變快（仍約 22–24 秒）；緩衝區放大只讓單次快約 5–20%。
不要用 thread：多個 Accounting 同時在記憶體裡，會撐爆記憶體。

## Accounting 一次請求的時間分解（qa/stress/stages.py；6,900 件已公布／已確認案件，共約 21–23 秒）
| 階段 | 秒 | 說明 |
|---|---|---|
| 讀資料庫（含整份 payload） | 3–5 | 讀約 180 MB |
| 複製 payload（deepcopy） | 1.3 | 每件案件整份複製 |
| 付款排程列 ledger_rows | 5.3 | 其中有收款的案件（1,782 件）又把交易明細重算一遍，約 2.2 秒 |
| SoA 交易列 transaction_rows | 7.9 | transaction_details 7.5 秒，其中人工結清判斷（apply_transactions）約 2–4 秒 |
| 排序、整份回應再複製、轉 JSON | 0.8 + 1.4 + 1.2 | |
- build_payment_schedule 被呼叫 15,582 次（每件案件 2.3 次），合計 5.4 秒；每件案件只需算一次。
- 回應 45.7 MB，沒有單一欄位佔大宗（最大的只有 7%），瘦身空間有限；gzip 後 4.2 MB（9%），壓縮約 0.4 秒。
- 時間相依：付款狀態只取決於「台北今天日期」與「是否過了 12:00」，所以結果可以用 (案件 row_version、日期、12:00 前後) 當快取鍵。
- 前端 Accounting 表格是一般 el-table，沒有分頁或虛擬捲動，會把所有列（約 3 萬列）一次畫出；瀏覽器端時間尚未量測。
